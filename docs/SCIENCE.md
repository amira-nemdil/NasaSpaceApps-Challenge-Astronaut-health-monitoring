# Methodology, datasets and safety limits

## What the challenge asks

NASA Space Apps 2026's **Create Health Monitoring Software for Astronauts on Space Missions** asks for a system gathering indicators and enabling astronauts to evaluate and act on their health status during long-duration exploration.

Official challenge: https://www.spaceappschallenge.org/2026/challenges/health-monitoring-software/

## Data provenance

The prototype's astronaut profiles, day-by-day values, synthetic scenario shifts and alert rules are **entirely generated by this project**. They are not NASA astronaut biometric records, nor are they derived from a clinical cohort. Do not write "trained on NASA astronaut data" in the pitch.

A NASA Space Apps discussion notes that there is no single mandatory downloadable set of real astronaut vitals prescribed for this challenge: https://github.com/nasa/spaceapps/discussions/2025

NASA's Open Science Data Repository https://osdr.nasa.gov/ is a **research source for future work**; the code does not download data from it.

## Current monitoring logic

For a given synthetic astronaut and signal \(x\):

- Baseline is the first seven simulated days, with arithmetic mean \(\mu\) and population standard deviation \(\sigma\).
- We use a **variability floor** \(f\) to avoid tiny manufactured variability making trivial changes look enormous.
- A directional deviation score is \(z = (x - \mu)/\max(\sigma,f)\) for rising heart rate and fatigue, and \(z = (\mu-x)/\max(\sigma,f)\) for falling sleep and mood.
- If any \(z\ge1.8\), flag **watch**. If any \(z\ge2.8\) or two or more indicators have \(z\ge1.8\), flag **review**.

**Every number above is a demo engineering choice, NOT a clinical threshold, validated biomarker limit, or astronaut-specific safety rule.** This is transparent statistical monitoring; it should not be advertised as supervised or validated AI. It is possible to replace the engine with Isolation Forest when real, usable research data is secured, but that work is not yet implemented.

## Recommended crew workflow

A flagged state means: re-check data quality, document symptoms or workload, and use established flight-medical protocols or contact the flight medical team. Never prescribe drugs, diagnose diseases, or generate urgent actions from synthetic trends.

## NASA event reporting

The `GET /api/space-weather` endpoint retrieves real, publicly reported **Solar Energetic Particle (SEP) event metadata** from NASA DONKI where available. It is not a measurement of the dose inside a spacecraft or to any astronaut, and cannot estimate crew radiation risk without spacecraft shielding, location, instruments and specialist modelling.

Documentation: https://api.nasa.gov/ and https://ccmc.gsfc.nasa.gov/tools/DONKI/

The NASA request is optional and fails safely; the app makes no fake "live NASA events" when offline. Health telemetry remains local and simulated.

## Improvements after the hackathon

1. Read mission medical standards and ask clinicians to set appropriate use boundaries.
2. Find fit-for-purpose, licensed datasets and document informed consent/privacy practices.
3. Evaluate whether baseline anomaly detection is robust under sensor noise, missing data, individual differences, and adaptation to microgravity.
4. Add explicit missing-data handling, audits, and secure local storage.
5. Study constraints of long-duration missions and evaluate local-first operation when network access is intermittent.

**Disclaimer:** AstroPulse is an educational hackathon prototype and not a medical device or flight-qualified system.
